## Git 협업 규칙

### 1. 브랜치 운영

| 브랜치 | 용도 | 분기 기준 | 병합 대상 |
|---|---|---|---|
| `main` | 배포 가능한 안정 버전 | — | — |
| `develop` | 개발 기능을 통합하는 브랜치 | `main` | `main` |
| `feature/*` | 새로운 기능 개발 | `develop` | `develop` |
| `fix/*` | 개발 중 발견한 오류 수정 | `develop` | `develop` |
| `hotfix/*` | 배포 버전의 긴급 오류 수정 | `main` | `main`, `develop` |

- 일반 개발은 `develop`에서 작업 브랜치를 만들어 진행한다.
- `main`과 `develop`에 직접 푸시하지 않고 PR로 병합한다.
- `develop`의 기능을 검증한 뒤 `main`으로 배포 PR을 생성한다.
- 별도의 `release` 브랜치는 초기에는 사용하지 않는다.
- `hotfix` 수정 사항은 `develop`에도 반영해 다음 배포에서 사라지지 않도록 한다.
- 병합이 완료된 작업 브랜치는 삭제한다.

### 2. 브랜치 이름

`종류/이슈번호-작업내용` 형식을 사용한다.
작업 내용은 영문 소문자와 하이픈으로 작성한다.

예시:

- `feature/12-firebase-login`
- `feature/18-case-upload`
- `feature/23-roi-analysis`
- `fix/31-invalid-roi`
- `hotfix/40-login-error`

### 3. 기본 작업 순서

1. 작업할 내용을 Issue로 등록한다.
2. 담당자와 완료 조건을 작성한다.
3. 최신 `develop`에서 작업 브랜치를 생성한다.
4. 구현하고 직접 동작을 확인한다.
5. 의미 있는 변경 단위로 커밋한다.
6. 작업 브랜치를 푸시하고 `develop` 대상 PR을 생성한다.
7. 다른 팀원 1명 이상의 리뷰와 승인을 받은 뒤 병합한다.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/12-firebase-login

# 코드 작성 및 확인 후
git add src/auth/firebase_auth.py src/ui/login.py
git commit -m "feat(auth): 이메일 로그인 기능 추가"
git push -u origin feature/12-firebase-login
```

작업 중 `develop`의 변경 사항을 반영할 때:

```bash
git fetch origin
git merge origin/develop
```

충돌을 해결한 뒤 관련 기능을 다시 확인하고 푸시한다.

### 4. 커밋 메시지 규칙

형식:

```text
type(scope): 작업 내용
```

`scope`는 선택 사항이며, 변경한 기능이나 모듈을 적는다.

| Type | 사용 상황 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 오류 수정 |
| `refactor` | 동작 변경 없이 코드 구조 개선 |
| `docs` | README와 설계 문서 수정 |
| `test` | 테스트 추가와 수정 |
| `style` | 공백, 들여쓰기 등 코드 형식 수정 |
| `chore` | 의존성, 개발 도구, 설정 변경 |
| `ci` | GitHub Actions 등 자동화 설정 변경 |
| `revert` | 이전 변경 되돌리기 |

예시:

```text
feat(case): 케이스 등록 기능 추가
feat(roi): 관심 영역 평균과 분산 계산 추가
fix(auth): 로그아웃 후 사용자 정보가 남는 오류 수정
refactor(storage): 영상 파일 저장 로직 분리
docs: 로컬 실행 방법 추가
test(review): 빈 리포트의 완료 처리 거절 검증
chore: OpenCV 의존성 추가
```

- 제목은 무엇을 변경했는지 구체적으로 작성한다.
- `수정`, `작업`, `최종`, `update`처럼 내용이 불분명한 메시지는 피한다.
- 관련 없는 변경은 별도 커밋으로 나눈다.
- `style`은 화면 디자인 변경을 뜻하지 않는다. 화면 기능 추가는 `feat`, 화면 오류 수정은 `fix`를 사용한다.

### 5. Issue 작성 규칙

Issue에는 다음 내용을 포함한다.

- 목표: 어떤 기능이나 문제를 다루는지
- 담당자: 실제 작업할 팀원
- 완료 조건: 무엇을 확인하면 끝난 것으로 볼지
- 선행 작업: 먼저 완료돼야 하는 Issue
- 관련 요구사항: 해당하는 기능 ID가 있다면 기재

예시:

```text
제목: [기능] 케이스 등록

목표
관리자가 모의 케이스를 등록할 수 있다.

완료 조건
- 필수 정보를 입력하면 등록된다.
- 필수 정보 누락 시 오류를 안내한다.
- 등록한 케이스가 목록에 표시된다.
- 권한 없는 사용자의 등록 요청을 거절한다.
```

### 6. Pull Request 규칙

- PR 하나에는 하나의 작업 목적을 담는다.
- 병합 대상 브랜치가 `develop`인지 확인한다.
- 작성자 외 팀원 1명 이상의 승인을 받는다.
- 리뷰 후 변경한 코드도 확인받고 병합한다.
- 테스트 실패와 해결하지 않은 충돌이 있으면 병합하지 않는다.
- 기능 작업 PR은 Squash merge를 기본으로 사용한다.
- `develop → main` 배포 PR은 merge commit 방식으로 병합한다.

PR 본문:

```text
## 관련 Issue
Refs #12

## 변경 내용
- 이메일과 비밀번호 입력 화면 추가
- Firebase 로그인 요청 연결

## 확인한 내용
- 정상 계정 로그인
- 잘못된 비밀번호 오류 표시
- 로그아웃 후 접근 제한

## 참고 사항
- 추가 설정이나 알려진 제한 사항
```

Issue는 병합 후 완료 조건을 확인하고 닫는다.

### 7. 코드리뷰 기준

- 요구사항에 맞게 동작하는가?
- 권한과 상태 조건을 검사하는가?
- 잘못된 입력과 실패 상황을 처리하는가?
- 기존 기능에 영향을 주지 않는가?
- 화면, 업무 로직, 저장 코드의 책임이 구분돼 있는가?

단순한 취향 차이는 제안으로 남기고, 오류와 요구사항 누락은 수정 요청으로 구분한다.

### 8. 공통 주의사항

- 비밀번호, 서비스 계정 키, 토큰을 커밋하지 않는다.
- `.env`, `.streamlit/secrets.toml`, 개인 인증키는 `.gitignore`에 등록한다.
- 공유 브랜치에서 강제 푸시하지 않는다.
- 다른 팀원이 사용하는 함수나 데이터 구조를 바꾸면 먼저 공유한다.
- 실제로 수행한 검증 결과만 Issue와 PR에 기록한다.
