# 의료영상 처리 및 검토 업무 관리 시스템

## 통합 기능 명세서

### 1. 문서 개요

#### 1.1 목적

- 본 문서는 의료영상 처리 및 검토 업무 관리 시스템에서 제공해야 하는 기능과 사용자별 접근 권한을 정의한다.
- 프로젝트 구성원들이 동일한 기능 요구사항을 기준으로 화면 설계, API 개발, 데이터베이스 구현 및 테스트를 진행할 수 있도록 하는 것을 목적으로 한다.

#### 1.2 시스템 개요

- 본 시스템은 모의 의료영상 데이터를 기반으로 케이스를 등록하고, 검토 담당자를 배정하여 의료영상 처리와 검토 업무를 수행하는 웹 기반 시스템이다.
- 사용자는 부여된 권한에 따라 케이스를 조회하거나 영상처리를 수행하고, 처리 결과와 검토 기록을 저장·조회할 수 있다.

#### 1.3 기술 구성

| 구분 | 기술 |
| --- | --- |
| 사용자 인터페이스 | Streamlit |
| 사용자 인증 | Firebase Authentication |
| 데이터베이스 | PostgreSQL(구현 후보) |
| 의료영상 저장 | 별도 파일 스토리지 |
| 영상처리 | Python 기반 영상처리 라이브러리 |

#### 1.4 사용자 구분

| 사용자 구분 | 설명 |
| --- | --- |
| 관리 및 운영 담당자 (M) | 사용자 관리, 케이스 등록, 영상 업로드, 검토 담당자 배정 및 업무 현황 조회 |
| 배정된 검토 담당자 (R) | 자신에게 배정된 케이스의 영상처리, 분석, 검토 및 기록 작성 |
| 조회만 허용된 검토 담당자 (V) | 조회 권한이 부여된 케이스의 영상, 처리 결과, 검토 기록 열람 |

**권한 정의 원칙**

- M은 시스템 운영을 위한 관리 역할이다.
- R과 V는 개별 케이스에 대해 부여되는 접근 권한을 의미한다.
- 동일한 사용자가 케이스에 따라 R 또는 V 권한을 가질 수 있다.
- 사용자 역할과 케이스별 접근 권한을 함께 확인하여 기능 실행 여부를 결정한다.

#### 1.5 구현 우선순위

| 구분 | 의미 |
| --- | --- |
| P0 | 핵심 업무 흐름을 구성하는 우선 구현 기능 |
| P1 | 세부 관리 또는 추가 편의 기능으로 후순위 구현 가능 |

P0/P1은 프로젝트 개발을 위한 잠정적 우선순위이며, 과제 PDF의 공식 필수·선택 기능 분류는 아니다.

- 인증되지 않은 사용자는 케이스 및 의료영상에 접근할 수 없다.
- 사용자 역할에 따른 기능 권한을 확인해야 한다.
- 케이스별 접근 권한을 가진 사용자만 해당 데이터를 조회할 수 있다.
- 화면뿐 아니라 서버 API에서도 접근 권한을 검증한다.
- 일반적인 Firebase 로그아웃은 클라이언트 로그인 상태를 종료하는 동작이며, 이미 발급된 토큰의 즉시 폐기와는 구분한다.

- 케이스에 검토 담당자가 배정되면 해당 담당자가 자신의 업무 목록에서 확인할 수 있어야 한다.
- 케이스 삭제 또는 보관 기능은 P1로 분류하고 구현 범위를 별도로 확정한다.

- 영상 데이터 조회 시 해당 케이스에 대한 접근 권한을 확인한다.
- 원본과 처리 결과 영상의 연결 관계를 유지한다.

- 영상처리 실행은 배정된 검토 담당자만 수행할 수 있다.
- 영상처리 실행 전에 입력값의 유효성을 검사한다.
- 처리 결과를 저장할 때 원본과 결과를 구분한다.
- 실행 당시 사용한 알고리즘 및 파라미터를 기록한다.
- 저장된 처리 결과는 나중에 다시 조회할 수 있어야 한다.

| REV-02 | 담당 케이스 조회 | 자신에게 배정된 검토 업무 목록과 상태를 확인한다. | R | P0 | 케이스, 케이스 담당자 | 2~3쪽 |
| REV-03 | 검토 시작 | 케이스 상태를 검토 중으로 변경한다. | R | P0 | 케이스 | 2~3쪽 |
| REV-04 | 검토 메모 작성 | 의료영상 검토에 대한 메모를 작성하고 저장한다. | R(검토 중) | P0 | 케이스, 검토 기록 데이터 | 2, 7쪽 |
| REV-05 | 검토 메모 수정 | 작성한 메모를 변경한다. | R(검토 중) | P1 | 검토 기록 데이터 | 확인 필요 |
| REV-06 | 검토 리포트 작성 | 영상과 처리 결과에 대한 요약 리포트를 작성하고 저장한다. | R(검토 중) | P0 | 검토 기록 데이터 | 2, 7쪽 |

| REV-08 | 재검토 요청 | 재검토가 필요한 케이스의 상태를 변경하고 요청 사유를 기록한다. | R(허용 조건) | P1 | 케이스, 검토 기록 데이터 | 확인 필요 |
| REV-09 | 검토 기록 조회 | 저장된 메모와 리포트를 작성자 및 작성 시간과 함께 조회한다. | M/R/V | P0 | 검토 기록 데이터 | 2, 7쪽 |

**기능 규칙**

- 검토 상태 변경은 해당 케이스에 배정된 검토 담당자만 수행한다.
- 검토 메모와 리포트는 검토 중 상태에서 작성할 수 있다.
- 검토가 완료되면 케이스의 진행 상태가 갱신되어야 한다.
- 저장된 검토 기록에는 작성자와 작성 시간을 포함한다.
- 조회 전용 권한을 가진 사용자는 검토 기록을 변경할 수 없다.

### 10. 데이터 관리 요구사항

본 프로젝트는 기존 8개 테이블을 기반으로 기능을 구현하며, 초기 개발 단계에서는 새로운 테이블을 추가하지 않는 것을 원칙으로 한다.

| 테이블 | 관련 기능 |
| --- | --- |
| 사용자 | AUTH, CASE, REV |
| 진료과 | AUTH, CASE |
| 환자 | CASE |
| 케이스 | CASE, REV, HIST |
| 케이스 담당자 | AUTH, CASE, REV |
| 처리 종류 | PROC |
| 처리 결과 | PROC, HIST |
| 파일 정보 | FILE, VIEW, PROC |

**기존 데이터 구조의 최소 보완 사항**

- 케이스의 검사 종류·검사 부가 정보·검사 시간·등록자 ID를 정식 필드로 확정한다.
- 케이스 담당자 테이블에서 검토 배정과 조회 전용 권한을 구분할 수 있도록 한다.
- 처리 결과에 알고리즘 파라미터를 저장한다.
- 처리 결과에서 ROI 분석 기록(ROI 영역과 통계)을 관리한다.
- 파일 정보에서 파일 메타데이터(원본 파일명, MIME 타입, 크기, 업로드한 사용자)를 관리한다.
- 케이스에서 검토 메모와 리포트 기록을 관리한다.
- 복잡한 변경 감사 이력은 초기 구현 범위에서 제외한다.

검토 기록은 초기 구현 규모를 고려하여 케이스 문서의 Firestore Array로, ROI 분석 기록은 처리 결과 문서의 Map 필드로 관리한다. 다만 개별 기록의 복잡한 검색·수정·감사 기능까지 제공하는 구조는 아니다. 세부 필드는 Firestore DB 설계서 v1.3(`04_Architecture_Data.md`)을 따른다.

### 11. 핵심 업무 시나리오

**시나리오 1 — 케이스 등록 및 담당자 배정**

1. 관리 및 운영 담당자가 로그인한다.
2. 모의 환자와 검사 정보를 입력하여 케이스를 등록한다.
3. 원본 의료영상을 업로드한다.
4. 시스템이 파일을 검증하고 저장한다.
5. 검토 담당자를 지정한다.
6. 배정된 케이스가 검토 담당자의 업무 목록에 표시된다.

**시나리오 2 — 영상처리 및 검토**

1. 검토 담당자가 자신의 케이스를 조회한다.
2. 케이스를 열어 원본 영상을 확인한다.
3. 검토 상태를 검토 중으로 변경한다.
4. 영상처리 알고리즘과 파라미터를 설정한다.
5. 영상처리를 실행한다.
6. 원본과 처리 결과를 비교한다.
7. 필요에 따라 ROI 분석을 수행한다.
8. 처리 결과와 분석 기록을 저장한다.
9. 검토 메모와 요약 리포트를 작성한다.
10. 검토를 완료한다.

**시나리오 3 — 결과 및 기록 조회**

1. 사용자가 로그인한다.
2. 조회 권한이 있는 케이스를 검색한다.
3. 케이스의 원본 및 처리 결과 영상을 조회한다.
4. 저장된 ROI 분석 결과를 확인한다.
5. 이전 영상처리 설정값과 결과를 조회한다.
6. 검토 메모, 리포트 및 작성 정보를 확인한다.

### 12. 구현 범위 및 관리 원칙

**12.1 초기 구현 범위**

초기 구현에서는 P0 기능과 핵심 업무 시나리오의 정상 동작을 우선한다.

P1 기능은 프로젝트 일정과 과제 요구사항 확인 결과에 따라 구현 여부를 결정한다.

**12.2 데이터베이스 설계 원칙**

- 기존 8개 테이블을 유지한다.
- 필수 기능에 필요한 최소한의 속성만 추가한다.
- 의료영상 원본은 별도 스토리지에 저장한다.
- 영상처리 결과는 원본과 분리하여 보존한다.
- 사용자별 권한 검사는 서버에서 수행한다.
- 기능 명세에서 요구하지 않는 복잡한 감사 로그 및 이력 체계는 추가하지 않는다.

**12.3 기능 변경 관리**

기능을 추가·수정·삭제하는 경우 해당 기능 ID를 기준으로 변경 사항을 관리한다.

기능 변경 시 화면 동작, API, 데이터 저장 구조, 사용자 권한에 미치는 영향을 확인한다.

**12.4 최종 확인 사항**

- 원본 과제 PDF와 각 기능의 필수 여부 및 근거 페이지 일치 여부
- 케이스당 검토 담당자 수
- 조회 권한 부여·회수 방식
- 검토 상태 전이 규칙
- 검토 리포트 저장 형식
- ROI 분석 기록의 저장 항목
- P1 기능의 최종 구현 여부
